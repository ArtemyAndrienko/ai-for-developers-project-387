## Стек

- Бэкенд: **Go 1.27** (закреплён в `mise.toml`), стандартный `net/http` без рамок; внутреннее
  хранилище — **Go-структуры данных** в памяти (`sync.RWMutex` + map), в перспективе заменяется на
  embedded-хранилище с сохранением тех же методов
- Фронтенд: **TypeScript + Vite** (vanilla TS без UI-фреймворка), юнит-тесты логики — **Vitest**
- Сборка и версии инструментов: **mise** (`mise.toml` закрепляет go 1.27.4 и node 24.22.2, задачи
  `dev`, `test`, `build`), зависимости фронтенда — npm + lockfile
- API: JSON REST (`/api/...`). Контракт — **цепочка TypeSpec → OpenAPI 3 → SDK**:
  `typespec/main.tsp` компилируется эмиттером `@typespec/openapi3` в
  `typespec/tsp-output/@typespec/openapi3/openapi.json`, оттуда `openapi-typescript`
  генерирует типы клиента `frontend/src/api/schema.d.ts`, а типобезопасные вызовы
  делает `openapi-fetch` (`frontend/src/api.ts` — тонкая обёртка, `types.ts` — только
  ре-экспорт схем). Сверка маршрутов Go ↔ спецификация: `mise run check-contract`.
  В dev-режиме фронтенд проксирует `/api` на `:8080` (vite)

### Структура

```
backend/    # Go: main.go (HTTP), store.go (in-memory хранилище), slots.go (генерация интервалов)
frontend/   # Vite + TS: src/views/{book,create,mine}.ts, calendar.ts, api.ts (SDK-обёртка) + тесты
typespec/   # контракт API: main.tsp -> tsp-output/@typespec/openapi3/openapi.json
scripts/    # check-contract.sh — сверка маршрутов Go и OpenAPI
mise.toml   # закреплённые версии инструментов и задачи сборки
```

Ручная правка контракта: меняем `typespec/main.tsp`, затем `mise run codegen` — типы
фронтенда (`src/api/schema.d.ts`) пересоберутся, а расхождение с Go поймает
`mise run check-contract` (он же часть `mise run test`).

## Функциональные сценарии

Сервис работает по модели «организатор → посетитель»: первый создаёт встречу со свободными
интервалами, второй записывается на один из этих интервалов. Приложение состоит из трёх экранов
(по референсам): лендинг с навигацией «Записаться» / «Предстоящие события», экран «Запись на
звонок» и экран «Предстоящие события».

### Сценарий 1. Создание встречи

**Участник:** организатор.
**Цель:** создать встречу, назначенную на конкретный день и разбитую на интервалы указанной
продолжительности, на которые смогут записываться другие пользователи. Конкретный интервал
организатор **не выбирает** — сетка интервалов показана ему как превью доступности.
**Предусловия:** границы рабочего дня (время начала и окончания) применяются **к конкретному дню,
на который назначена встреча, и сопоставляются по адресу email организатора**. Если для пары
(организатор, дата) границы не сохранялись, по умолчанию используется интервал 09:00–18:00
(полный рабочий день даёт 18 интервалов по 30 минут).

**Ход сценария:**

1. Пользователь открывает форму создания встречи и заполняет поля:
   - название — обязательно;
   - описание — необязательно;
   - email организатора — обязателен: по нему проверяется занятость временны́х интервалов
     этого пользователя во всех его встречах;
   - имя организатора — необязательно: отображается посетителям в «Моих записях»
     рядом с названием встречи (имя и/или почта);
   - дата встречи — выбирается в календаре справа (встреча назначается на этот день);
   - продолжительность интервала — обязательна (например, 15 / 30 / 60 минут);
   - шаг стартов — необязательный (ADR-0003): «как длительность» (поведение по умолчанию) или
     плотнее — пресеты от 15 минут и не больше выбранной длительности.
2. Справа от формы отображается календарь с окном доступности 14 дней. В референсе он реализован
   как сетка месяца (недели Пн–Вс) с кнопками листания по неделям ← / → и заголовком месяца
   («март 2026 г.»).
3. В ячейке каждого доступного дня отображается количество свободных интервалов (бейдж вида «18 св.»).
   Дни в прошлом и дни за пределами 14-дневного окна подсвечены серым и не выбираются.
4. При выборе дня показывается список интервалов заданной продолжительности: рабочий день
   этого организатора на эту дату разбивается от времени начала до времени окончания, старты
   идут с выбранным шагом стартов, пока полная длительность влезает в день (например, при
   длительности 30 и шаге 30 — «09:00 - 09:30», «09:30 - 10:00», …; при 60/30 — «09:00 - 10:00»,
   «09:30 - 10:30», …). Границы выводятся из сохранённых для пары (email, дата) либо по
   умолчанию 09:00–18:00.
5. «Хвостовой интервал» упразднён: остаток дня короче продолжительности не предлагается вообще —
   в превью видны только бронируемые целые интервалы (ADR-0003).
6. Список интервалов показывает превью доступности: интервалы, уже занятые бронями в **других встречах
   того же организатора на ту же дату** (пересечение временны́х отрезков, даже если сетки интервалов
   разные), помечаются как занятые — выбрать их нельзя.
7. Пользователь может сохранить границы рабочего дня **только для конкретной даты** встречи.
   Это обновление превью на месте: форма создания не перезагружается, введённые название,
   описание, email и дата сохраняются; остальные даты и других организаторов изменение не касается.
8. Пользователь сохраняет встречу: кнопка сохранения неактивна, пока не заполнены название,
   email организатора и не выбрана дата. Созданная встреча становится доступна для записи.

**Статусы интервалов:**

| Статус | Вид | Можно выбрать |
| --- | --- | --- |
| Свободный | обычный, метка «Свободно» | да (посетителю) |
| Занятый (бронь этой или другой встречи того же организатора) | серый, метка «Занято» | нет |
| Прошедший (день/время в прошлом) | серый | нет |

**Проверки при сохранении:**

- название непустое, длина в пределах лимита;
- email организатора непустой и имеет корректный формат;
- продолжительность — положительное значение из допустимого диапазона;
- шаг стартов, если задан, — целый от 1 до продолжительности включительно (иначе 422);
- дата встречи выбрана, входит в 14-дневное окно доступности и не в прошлом;
- границы рабочего дня на дату валидны (начало раньше окончания), иначе применены дефолтные
  09:00–18:00.

Ошибки показываются рядом с полем, встреча не сохраняется.

**Результат:** после сохранения отображается список всех встреч пользователя, включая только что
созданную. Если встреч нет, список пустой — показывается пустое состояние с предложением создать
первую встречу.

**Граничные случаи:**

- рабочий день короче одной продолжительности → сетка пуста: целых интервалов нет,
  превью пустое, сохранение недоступно с подсказкой уменьшить длительность или сдвинуть
  границы дня (хвостов не рисуется, ADR-0003);
- день без свободных интервалов → бейдж «0 св.» или его отсутствие, все интервалы в списке помечены
  как занятые;
- сохранение границ дня на одну дату не меняет превью и доступность других дат этого же
  организатора и других организаторов;
- интервалы строятся в локальном времени сервера, при сохранении новых границ на дату
  пересчитывается только ещё не забронированное.

### Сценарий 2. Запись на свободное время

**Участник:** любой пользователь, аккаунт не требуется — запись идентифицируется по e-mail.
**Цель:** выбрать доступную встречу, забронировать свободный интервал и увидеть свои записи.
**Предусловия:** у организатора есть хотя бы одна встреча со свободными интервалами.

**Ход сценария:**

1. Пользователь открывает экран «Запись на звонок» (кнопка «Записаться» с лендинга) и видит
   список доступных встреч: карточки с названием, датой (встреча уже назначена на конкретный
   день), описанием и длительностью интервала. Экран в пилоте состоит из двух колонок:
   - «Информация» — карточки «Встреча», «Дата», «Выбранное время», «Свободно» (число интервалов дня),
     «Длительность интервала»; до выбора в них отображаются прочерки и «Время не выбрано»;
   - «Статус интервалов» — пока встреча не выбрана, показывается подсказка «Выберите встречу выше.»,
     кнопка «Продолжить» неактивна.
   (В референсе экран трёхколоночный с календарём на 14 дней — там выбор дня и интервала
   разделены; у встречи с фиксированной датой день задаёт организатор.)
2. Пользователь выбирает встречу — в «Статусе интервалов» появляется список интервалов её дня
   со статусами «Свободно» / «Занято» / «Прошло»; занятые и прошедшие интервалы неактивны.
   Границы дня берутся из настроек организатора на эту дату (по умолчанию 09:00–18:00).
3. Пользователь выбирает свободный интервал (подсветка, «Выбранное время» обновляется) и нажимает
   «Продолжить». Кнопка «Назад» снимает выбор интервала без потери выбранной встречи.
4. Открывается блок «Подтверждение записи»: поля «Имя» и «Email», кнопка «Подтвердить запись»,
   кнопка «Изменить» для возврата к выбору интервала.
5. При подтверждении система проверяет конфликт: если интервал успели забронировать, показывается
   ошибка «интервал занят» и пользователь возвращается к выбору интервала.
6. Успешная запись: «Бронь подтверждена. До встречи!» с кнопкой «Забронировать ещё» (повторная
   запись в том же окне). Занятый интервал немедленно становится неактивным («Занято»), счётчики
   пересчитываются («Свободно 18» → «Свободно 17», бейдж дня «18 св.» → «17 св.»).
7. Пользователю отображается экран «Предстоящие события» со списком его записей; карточка записи
   содержит имя, e-mail, начало интервала («Интервал: 2026-03-28-09:00») и дату создания записи
   («Создано: 27.03.2026, 14:40»), а напротив названия встречи — данные организатора:
   имя и/или email организатора (email есть всегда, имя — если его указали при создании).
   Если записей нет — пустой список с предложением записаться.

**Проверки и конфликты:**

- имя и e-mail обязательны, e-mail валиден;
- запись невозможна на занятый, прошедший или серый (недостаточный) интервал;
- повторная запись на тот же интервал блокируется проверкой конфликта;
- занятость считается по времени **организатора встречи**: если интервал пересекается с бронью в
  другой встрече того же организатора (даже с другой сеткой интервалов), запись невозможна —
  «интервал занят»; у встреч других организаторов это время остаётся свободным.

**Отображение статуса встреч:**

- по умолчанию список делится на две группы: «Предстоящие» и «Прошедшие»;
- как только время встречи закончилось, она переносится в группу «Прошедшие» — отдельно
  перемаркировать её вручную не нужно;
- «Прошедшие» отображаются по умолчанию и скрываются по кнопке «Скрыть неактуальное»
  (повторное нажатие — «Показать неактуальное», выбор состояния сохраняется для пользователя).

**Результат:** пользователь видит предстоящие встречи с датой, временем, названием и контактами,
а прошедшие — в отдельной свёрнутой группе. Отменённая организатором Встреча исчезает из
списков доступных, а её Записи остаются в истории «Мои записи» с пометкой «Отменена ·
отменено организатором»; освободившийся Интервал снова свободен для записи.

**Отображение времени Посетителю** (билет #13 карты): первичны часы Организатора с подписью
пояса (`UTC+3`/`MSK`, IANA в подсказке) и локальным временем браузера в скобках;
календарные даты окна и «сегодня» — дни Организатора; история «Мои записи» — то же правило.

## Дальнейшее развитие

Закрыто ноябрьской итерацией: SQLite-хранилище (ADR-0001), лендинг с hash-роутером,
предупреждение посетителя о пересечении с его собственной предстоящей записью,
статус «Отменена» для Записи (Отмена Записи Посетителем и мягкая Отмена Встречи
Организатором с сохранением истории в «Мои записи»), часовые пояса — IANA-зона
Организатора в его профиле, сетка/даты/«прошло» якорятся к его часам, `tzdata`
в бинаре (билет #4, ADR-0004), скользящий шаг стартов — необязательный
`startStepMin` Встречи (дефолт = длительность, диапазон 1–duration) и упразднение
«Хвостового интервала» (билет #3, ADR-0003), отображение Посетителю — часы
организатора с подписью пояса и локальным временем в скобках (билет #13).

Осознанные отложения, чтобы не забыть переделать:

- **Идентичность Организатора**: email самодекларируемый (форма/localStorage),
  без подтверждения и авторизации.

## Тесты

Политика — принцип верхнего достаточного шва ([ADR-0005](docs/adr/0005-testing-boundaries.md)):
каждое доменное правило проверяется на самой высокой границе, где оно полностью
выражается; дубли через границы — smell.

- **Чистые функции**: Go unit (сетка интервалов, парсеры времени), Vitest
  (календарная сетка, роутер, конфликты посетителя);
- **Store + SQLite**: доменные правила на `:memory:` — сквозная занятость,
  границы по (email, дата), отмены, персистентность через перезакрытие базы;
- **Контракт**: `scripts/check-contract.sh` — маршруты и методы OpenAPI ↔ Go,
  часть `mise run test`;
- **HTTP e2e** (`backend/e2e_test.go`, билет #15): happy-цикл по реальному
  роутеру (`httptest.Server` поверх `newMux`) и параллельная гонка бронирования —
  свойства, которые не возникают ниже Store-шовна.

`mise run check` = линтеры + тесты + контракт + сборка; тот же набор CI гоняет на каждый push.

первый запрос может идти ~минуту).

Единый образ: в multi-stage-сборке фронтенд собирается `npm run build` и
запекается в Go-бинарь через `go:embed` (`backend/web/dist`); один процесс
отдаёт SPA и `/api/*`, слушает **`$PORT`** (конвенция Render; приоритет
`ADDR > PORT > :8080`), есть liveliness-проб `GET /api/health`.

```bash
docker build -t calendar-app .
docker run -e PORT=8123 -p 8123:8123 calendar-app   # http://127.0.0.1:8123
```

Хостинг: docker-сервис на Render создаётся через render-MCP (конфиг —
`.opencode/opencode.json`, секрет берётся из переменной окружения
`RENDER_API_KEY`). Сборку на Render делает сам Render из `Dockerfile` на push
в `main` (auto-deploy).

Ограничение пилота: база SQLite — файл внутри контейнера (`DATA_PATH`, по
умолчанию `/srv/data/calendar.db`), **эфемерная**: редиплой или рестарт
обнуляют данные (free-план). Персистентность — отдельная задача (Render disk
или внешняя БД), как и авторизация.

## OpenCode-агент в GitHub Actions

Назначение: по упоминанию команды в комментарии запустить coding-агента прямо
на GitHub-раннере — разобрать и объяснить issue, внести правку или фичу
(агент создаёт ветку и открывает PR), ответить на замечание к конкретной строке
в PR. Конфиг — `.github/workflows/opencode.yml`.

- **События-триггеры**: `issue_comment` (обычные комментарии в issues и PR) и
  `pull_request_review_comment` (комментарии к строкам кода на вкладке Files)
  типа `created`. Автоматического запуска на создание issue/PR, по расписанию
  или вручную (`workflow_dispatch`) нет — только от реакции на комментарий.
- **Команды (mentions)**: явно используются `/opencode` и `/oc` — они заданы
  условием `if` в workflow (`contains` для строк нечувствителен к регистру) и
  совпадают с дефолтным набором экшена (`/opencode,/oc`, тоже без учёта
  регистра). Параметр `mentions` экшену не переопределяется: других
  триггерных фраз нет.
- **Модель**: `opencode/qwen3.8-flash` (формат `provider/model`, провайдер
  OpenCode Zen); ключ — репозиторий-секрет `OPENCODE_API_KEY`, передаётся
  экшену в одноимённой переменной окружения.
- **Аутентификация**: OIDC-режим (`id-token: write`) — раннер обменивает
  OIDC-токен на токен установленного GitHub-приложения opencode-agent;
  `use_github_token` не используется.
- **Публикация сессий (share)**: решение — **оставить включённой**: параметр
  `share` в workflow не задан, и для публичного репозитория это означает
  публикацию расшифровки сессии на `opencode.ai/s/…` (ссылка попадает в футер
  комментария агента) — для учебного проекта это демонстрация работы агента.
  Логика экшена: `share: false` → никогда; не задан + приватный репо → не
  публикуется; не задан + публичный → публикуется. Для отключения — добавить
  `share: false` в `with`.

**Результат**: ответ-комментарий агента в том же треде; для задач на исправку —
новая ветка и PR с изменениями; для построчных комментариев — ответ с
привязкой к файлу и строкам. GitHub берёт определение workflow из дефолтной
ветки (`main`), поэтому правки этого файла применяются после мержа в `main`.

### Автотриаж новых обращений (`.github/workflows/issue-triage.yml`)

Событие `issues` (`opened`/`reopened`) гоняет того же агента, но в роли
`triage` — ограниченный primary-агент из `.opencode/opencode.json`
(`edit: deny`). **Фильтры** (до запуска агента): только люди (не боты),
возраст аккаунта ≥ 30 дней (анти-спам), на issue уже нет канонического
триаж-лейбла, в заголовке нет `[skip-triage]`. **Права**: `GITHUB_TOKEN` —
`contents: read` + `issues: write` (запись нужна post-шагу, не агенту);
комментарий публикует opencode-app через OIDC. **Механика вердикта**: агент
выводит ровно один лейбл первой строкой ответа, а проставляет его workflow
(`Apply verdict label`) по маркеру своего прогона в комментарии — так лейбл не
зависит от того, придумает ли агент как его добавить. **Ограничения**:
`timeout-minutes: 15`; `wontfix` агенту запрещён (решение человека); во всех
`permission` явно `allow`/`deny` —headless-режим `opencode github run` (v1)
навсегда висит на любом `ask` (anomalyco/opencode#54477).

Вердикты раскладываются по канонам `docs/agents/triage-labels.md`:
`ready-for-agent` (полностью специфицирован — агент берёт его в работу без
дополнительных вопросов), `needs-info` (не хватает конкретики, вопросы
репортёру), `ready-for-human` (нужны действия человека), `needs-triage`
(безопасный дефолт, в том числе когда агент не ответил по форме).

## Что дальше
После успешной проверки проект можно развивать как продукт и добавлять новые возможности.

Гибкое расписание: окна доступности по дням недели, перерывы, исключения и праздничные дни.
Часовые пояса: хранение зоны владельца календаря и показ слотов для гостей из других регионов.
Регистрация и аккаунты: несколько пользователей, у каждого свои календари и типы встреч.
Интеграции с календарями: синхронизация занятости и событий с внешними сервисами.
Уведомления: напоминания о предстоящих событиях, подтверждения и отмены.
Дополнительные сценарии: перенос и отмена бронирований, повторяющиеся события, буфер между встречами, аналитика по записям.
